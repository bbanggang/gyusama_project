## 1. ONNX 변환 및 RPi5 Docker 배포 환경 구축

학습된 모델은 PyTorch 런타임 위에서만 동작해 작은 임베디드 보드(RPi5)에 그대로 올릴 수 없었음. 표준 모델 포맷인 ONNX로 변환하고, RPi5에 ROS2 Jazzy와 카메라·모터·LiDAR 드라이버를 묶은 Docker 컨테이너 4개를 구성. 각 컨테이너는 **추론 노드(inference-node, AI가 차선 박스를 찾는 부분), 장애물 감지 노드(obstacle-node, LiDAR로 앞에 무엇이 있는지 판단), 통합 의사결정 노드(behavior-node, 차선과 장애물 정보를 합쳐 최종 명령 만듦), 모터 제어 노드(control-node, TurtleBot3 드라이버 실행)** 로 역할이 분리됨. PC 빌드 이미지가 RPi5에서도 그대로 작동해, "PC와 로봇이 같은 환경"을 보장하는 배포 기반이 완성됨.

## 2. 시뮬레이션↔실물 호환성 분기 처리

같은 차선 추종 코드를 Isaac Sim과 실물에서 함께 쓰려는데, 두 환경의 ROS 메시지 형식이 달랐음. 모터를 움직이는 명령 메시지(`/cmd_vel` 토픽)가 Isaac Sim에서는 **`Twist`(속도 값만 담은 단순 형식)** 로 받지만, 실물의 ROS2 Jazzy 환경에서는 **`TwistStamped`(타임스탬프가 함께 들어간 새 형식)** 만 받음. 환경변수 하나로 두 형식을 자동 분기시키고, 동시에 모터 제어 보드(OpenCR — TurtleBot3에 들어있는 모터 마이크로컨트롤러)의 펌웨어를 ROS1용 → ROS2용으로 재플래시. 시뮬에서 검증한 코드가 실물에서 수정 없이 그대로 모터를 회전시키는 상태에 도달.

## 3. PC↔RPi5 크로스 머신 실시간 모니터링

RPi5에 모니터가 없어 카메라 영상이나 추론 결과를 보기 어려웠고, ROS2 기본 자동 발견 방식(같은 네트워크에 있는 노드끼리 알아서 찾아주는 멀티캐스트)이 공유기에서 차단되어 PC가 RPi5의 토픽을 발견 못 함. RPi5의 IP와 통신 포트를 직접 적은 통신 설정 파일을 PC에 적용해 IP를 정확히 지정하는 방식(유니캐스트)으로 우회. PC의 영상 viewer 도구(rqt_image_view)에서 **추론 결과 시각화 영상(`/lane/debug_image` 토픽 — 카메라 영상 위에 AI가 찾은 차선 박스와 텍스트 정보가 그려진 디버그 영상)** 을 실시간 볼 수 있게 되어 튜닝 사이클이 크게 짧아짐.

## 4. INT8 양자화 시도 → FP32 ONNX 배포 결정

CPU 추론이 초당 2장밖에 나오지 않아, 모델 가중치 숫자를 32비트 소수(FP32)에서 8비트 정수(INT8)로 압축하는 **양자화** 기법으로 속도를 올리려 시도. 그런데 캘리브레이션을 활성화 단계까지 모두 적용한 정적 INT8은 **mAP@50(평균 정밀도 — 검출 정확도 지표, 1.0이 만점)** 이 0.000으로 무너졌고, 가중치만 INT8로 줄인 동적 INT8도 mAP@50=0.432로 차선을 거의 못 잡음. 양자화 경로를 폐기하고 FP32 ONNX 그대로 배포하기로 결정, 속도 문제는 입력 해상도를 줄이거나 전용 AI 가속기 칩을 도입하는 방향으로 노선 변경.

## 5. Docker Hub 멀티아키텍처 빌드/자동 배포 파이프라인

기존 배포는 PC가 rsync로 매번 코드를 RPi5에 복사하고 컨테이너에 볼륨 마운트하는 구조라, RPi5가 PC에 종속되고 모델·코드 버전 불일치가 자주 발생. PC(인텔 x86 칩) 위에서 Docker의 멀티 아키텍처 빌드 도구(buildx)를 써서 RPi5용 ARM64(임베디드용 ARM 64비트) 이미지를 만든 뒤 Docker Hub(이미지 보관용 클라우드 저장소)에 업로드. RPi5는 `docker compose pull && up` 한 줄로 다운받아 실행. 코드와 모델이 이미지에 내장되어 RPi5 단독 운영이 가능하고, 시연 환경 이동 시에도 별도 셋업 없이 동일 환경 재현.

## 6. NCNN 추론 엔진 전환 + 320×320 모델 재학습

ONNX Runtime은 인텔 x86 CPU 위주로 최적화되어 RPi5의 ARM CPU에서는 효율이 떨어짐. ARM 칩의 병렬 처리 명령(NEON SIMD — 한 명령으로 여러 데이터를 동시 연산하는 ARM 표준 기능)에 고도로 튜닝된 Tencent의 **NCNN**(텐센트가 만든 모바일용 추론 라이브러리)으로 엔진을 교체. 동시에 모델 입력 해상도를 640×640 → 320×320으로 줄여 연산량을 1/4로 감소. 같은 합성 데이터로 yolov8n 320×320을 재학습한 결과 mAP@50=0.959 유지, RPi5 실측 FPS는 2 → 13~15로 약 8배 향상되어 임시 실시간 주행 가능 상태에 도달.

## 7. 합성 데이터 다양화 + 2000장 재생성

기존 1000장 합성 데이터는 카메라 위치·조명 변화 폭이 좁아서 학습 곡선이 크게 흔들렸고(마지막 20 에폭 동안 정확도 표준편차 0.196), 실제 카메라 입력과의 분포 갭도 컸음. 데이터 생성 스크립트에서 카메라 위치 ±10cm, 좌우 회전(yaw) ±15°, 상하 기울기(pitch) ±8°, 조명 강도/위치/색온도, 가우시안 노이즈와 블러까지 모두 무작위로 흔들어가며 2000장 재생성. 같은 yolov8n 320 모델로 재학습한 결과 mAP@50=0.962 + 마지막 20 에폭 표준편차 0.033(이전의 약 1/6)으로 학습 진동이 크게 감소해 실주행 안정성 향상.

## 8. APF 기반 차선 추종 + 장애물 회피 통합 — Isaac Sim 시나리오 검증

초기에는 LiDAR 기반 장애물 감지와 카메라 기반 차선 추종 로직이 한 노드 안에 섞여 있어, 어느 쪽에 문제가 있는지 분리해 디버깅하기 어렵고 우선순위(차선 따라가다 장애물 만나면 어떻게 할지)도 명확하지 않았음. **인공 포텐셜 필드(APF — Artificial Potential Field, 목표 지점이 로봇을 끌어당기는 인력과 장애물이 밀어내는 척력을 가중 합산해 한 방향 벡터로 만드는 고전 제어 기법)** 개념을 도입해, 차선 중심으로 끄는 인력(차선 추종 명령)과 장애물에서 밀어내는 척력(LiDAR 척력 벡터)을 가중합하는 통합 의사결정 노드(behavior-node)를 별도로 만들고, 책임을 3개 노드로 분리:

- **차선 추종 노드(lane_detect)**: 카메라 영상 → AI 추론 → 차선 중심 오프셋 → 차선 명령 토픽(`/lane/cmd_vel`)에 발행
- **장애물 감지 노드(obstacle_node)**: LiDAR 점들 → 영향권 안의 거리 + 방위 → 척력 계산 + 상태 토픽(`/obstacle/state`)에 clear/warn/avoid/stop 발행
- **통합 의사결정 노드(behavior-node)**: 위 두 토픽 받아 APF 합성 공식으로 최종 명령(`/cmd_vel`) 만듦
  - 합성식: 최종 angular = (1 − α) × 차선 명령 + K_rep × LiDAR 척력 (α는 장애물 가까울수록 차선 가중치 감소)
  - 4상태 머신: **clear**(영향권 내 장애물 없음, 차선 100%) → **warn**(영향권 진입, 감속 시작) → **avoid**(0.55m 진입, 회피 방향 고정) → **stop**(0.22m 진입, 즉시 정지)

Isaac Sim 환경용 별도 컴포즈 파일(`docker-compose.sim.yml` — 실물용과 분리, LiDAR 방향 보정 환경변수 `LIDAR_OFFSET_DEG=180` 적용)을 만들고 4개 시나리오를 통과시킴: (1) 직선 차선 + 정면 장애물 → clear→warn→avoid→stop 순차 발동 (2) 곡선 차선 + 측면 장애물 → 회피하면서 차선 인력 유지 (3) 다중 장애물 클러스터 → 진동 없이 한쪽으로 회피(latch 메커니즘) (4) 회피 후 자연스러운 차선 복귀(차선 가중치 자동 회복). 단일 노드 구조에서는 한 기능 버그가 전체에 영향을 주었던 데 비해, 분리 구조에서는 각 노드를 독립적으로 튜닝·재시작 가능해 디버깅 효율과 안정성이 동시에 향상.

## 9. Hailo-8 NPU 하드웨어/드라이버/컨테이너 통합

CPU + NCNN 조합으로는 안정적 30 FPS 확보가 어려워 전용 AI 가속기 칩(NPU = Neural Processing Unit, AI 추론 전용 칩)인 Hailo-8을 도입. RPi5의 확장 카드 슬롯(M.2)에 보드를 장착하고, 카드와 CPU를 잇는 통신 경로(PCIe — 확장 카드 통신 표준)를 Gen3(3세대, 약 8 Gb/s) 속도로 활성화. OS와 칩 사이의 다리 역할인 드라이버를 **커널 자동 재빌드 시스템(DKMS — 리눅스 커널이 자동 업데이트되어도 드라이버를 알아서 다시 컴파일해 주는 구조)** 으로 설치하고, NPU 통신 라이브러리(HailoRT)와 파이썬 인터페이스를 추가. 호스트에서 NPU 디바이스 노드(`/dev/hailo0`)가 인식된 뒤 Dockerfile에 통합해 컨테이너 안에서도 NPU가 보이게 함. 통합 과정에서 발견한 호환성 이슈 7건을 35분짜리 재현 가이드 문서로 정리해 보존.

## 10. NPU 전용 모델 컴파일 (양자화 + 다운사이즈)

NPU는 ONNX를 직접 읽지 못하고, 칩 전용 실행 포맷인 **HEF(Hailo Executable Format — Hailo 칩 위에서 직접 실행되도록 컴파일된 모델 파일)** 만 받음. PC에 Hailo의 모델 컴파일러(Dataflow Compiler, Docker 형태로 제공)를 설치해 변환 자동화 스크립트 작성. ONNX → 양자화 보정용 검증 이미지 100장 → 8비트 정수 양자화 → 칩 내부 자원(클러스터 8개 + 고속 메모리 SRAM)에 가중치를 배치하는 컴파일까지 한 줄로 처리. 처음에는 yolov8s 640과 yolov8n 640이 SRAM 한계로 컴파일 실패(`No valid partition` — 칩이 받아들일 수 있는 분할 방식을 못 찾음)했지만, yolov8n 320으로 다운사이즈해 HEF 9.5MB로 컴파일 성공. 모델 크기/입력 해상도와 NPU 메모리의 관계를 실측으로 학습한 결과.

## 11. NPU 전용 추론 노드 (lane_detect_hailo.py) 구현

HEF의 출력 텐서 구조가 ONNX/NCNN과 달라서 기존 코드로는 결과 해석이 불가. Hailo 컴파일러가 YOLOv8 모델을 검출 헤드 직전에 끊어 **bbox 위치 정보(2100개 후보 × 64채널 분포 데이터)** 와 **신뢰도(2100개 후보 × 1채널 sigmoid 값)** 두 개의 가공되지 않은 출력으로 내보냄. YOLOv8의 좌표 인코딩 방식인 **분포 회귀(Distribution Focal Loss — bbox 한 변의 거리를 0~15 사이 16개 구간 중 어디일 확률로 표현하고, 그 확률의 기댓값을 실제 거리로 환산하는 방식)** 를 디코딩하고, YOLO 표준 격자(stride 8/16/32로 화면을 격자 분할)에 매핑해 픽셀 좌표로 복원하는 후처리 모듈을 작성. 단위 테스트로 정확도 검증 후 기존 ROS2 인터페이스(차선 명령 토픽 `/lane/cmd_vel`, 디버그 영상 토픽 `/lane/debug_image`)를 그대로 유지해, 환경변수 하나로 NCNN↔NPU 즉시 토글 가능.

## 12. NPU 실주행 성능 검증 — 30 FPS 안정

NPU 도입 효과를 객관적으로 측정. Hailo가 제공하는 성능 측정 도구(`hailortcli benchmark` — 입력 더미 데이터를 반복 추론해 순수 NPU 속도만 잰다)로 측정 시 **NPU 단독 217 FPS / 1회당 3.97 ms latency**(NCNN 14.7 FPS 대비 약 15배). 실제 카메라 입력 → AI 추론 → 모터 명령(`/lane/cmd_vel` 토픽) 발행까지의 전체 흐름은 카메라 발행 속도(30 Hz)에 묶여 **실주행 30 FPS·한 사이클 33 ms**(NCNN 15 FPS 대비 2배). NPU 사용률은 50% 미만(클러스터 8개 중 4개, 평균 활용도 60%)으로 추가 후처리나 디버그 발행 부담을 흡수할 여유가 큼.

## 13. 실세계 파라미터 튜닝 (검출 안정화 + 진동 제어)

시뮬에서 잘 작동하던 파라미터를 실물에 그대로 가져왔더니 양자화로 인한 검출 신뢰도 분포 평탄화와 카메라 물리 장착 오차로 차선이 아닌 영역에 박스가 잡히고 좌우 진동이 발생. 검출을 인정할 최소 신뢰도(`conf_thresh` — 이 값 이상의 confidence를 가진 박스만 차선으로 인정)를 0.12 → 0.85로 단계적 상향, 검색 영역(ROI = Region Of Interest, 화면에서 차선을 찾을 범위)을 화면 하단 20%로 축소. 조향 명령 변환 계수(`kp_angular` — 차선 어긋난 정도 × 이 값 = 핸들 꺾는 양)를 11 → 4로 감소, 그리고 매 프레임의 노이즈를 부드럽게 만드는 **지수 이동 평균 필터**(Exponential Moving Average — 새 값 = 기존 평균 × (1−α) + 새 입력 × α, α가 작을수록 부드럽게 변함)를 추가. 각 변경의 영향을 분리해서 보기 위해 차선 추종만 단독으로 띄울 수 있는 `--lane-only` 모드(통합 의사결정 노드와 장애물 노드를 빼고 추론 노드가 모터 명령 토픽 `/cmd_vel`에 직접 발행)도 만들어 디버깅 효율 향상.

## 14. WiFi 대역폭 최적화 — 디버그 이미지 발행 경량화

시각 확인 모드(`PUBLISH_DEBUG=1`)에서 800×600 컬러 영상을 매 프레임 그대로 발행하니 데이터량이 1.4 MB/frame × 30 FPS ≈ 42 MB/s 가 되어, 한 사이클 처리 시간이 33 ms → 74 ms로 늘고 처리 FPS가 30 → 13으로 떨어짐. 디버그용 시각화 영상(`/lane/debug_image` 토픽)을 320×240으로 축소하고 발행 빈도를 1/3로 낮춰(3 프레임마다 한 번씩만 발행) 대역폭을 약 1/18로 감소. PUBLISH_DEBUG=1 상태에서도 처리 FPS 35 유지 + PC에서 rqt 화면 지연도 사실상 사라짐.

## 15. 환경 기동/종료 스크립트 자동화 + 예외 처리

수동 실행 시 4개 컨테이너와 카메라 노드, 모터 토크까지 일일이 챙겨야 했고, 리눅스 자동 업데이트로 커널이 바뀌면 NPU 드라이버가 새 커널용으로 빌드되지 않아 인식 실패, 또는 카메라 노드가 비정상 종료된 좀비 프로세스로 남아 카메라 디바이스를 점유하는 등 예외 케이스가 자주 발생. 시작 스크립트(`start_nodes.sh`)에 5단계 자동 검증을 넣음:
(1) NPU 인식 확인 + 미인식 시 드라이버 자동 재빌드 +  모듈 로드 / (2) 컨테이너 4종 모두 기동 확인 / (3) 카메라 노드 좀비 정리 후 새로 시작 / (4) 모터 토크 활성화 서비스(`/motor_power`) 자동 호출 / (5) NPU 모델 로드 로그 확인. `--debug` / `--lane-only` / `--no-obstacle` 옵션으로 노드 구성을 모드별 선택 가능. 종료 스크립트(`stop_nodes.sh`)도 모터 정지 명령 0,0 선발행 → 추론 노드 우선 종료 → 카메라 → 나머지 순서로 안전 종료하도록 정렬.

## 16. 안전 정책 + 최종 시연

자동 주행 옵션(AUTOSTART)은 사용자 의도와 무관하게 모터가 바로 움직여 위험할 수 있어 정책적으로 폐기. 주행 시작은 반드시 **추론 노드 컨테이너에 직접 들어가서**(`docker attach inference-node`) **`s` 키 입력**으로만 가능하게 고정. 종료는 `q` 키(모터 정지) 또는 `Ctrl+P, Ctrl+Q` 순차 입력(컨테이너는 살아있는 상태로 빠져나오기)만 허용. 직선 차선 추종 / 곡선 차선 추종 / 장애물 회피 / 회피 후 차선 복귀 시나리오를 통과한 최종 시연 영상을 촬영하고, 14주 진행 과정을 9개 챕터 + 트러블슈팅 사례 11건 + 본 보고서로 정리해 프로젝트를 마무리.
