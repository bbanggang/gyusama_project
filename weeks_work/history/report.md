# 규사마 프로젝트 핵심 보고서

> Isaac Sim 가상 센서 연동 / 차선·장애물 시스템 / 합성 데이터 / YOLOv8 학습 스크립트 이후부터
> 최종 시연까지 진행된 굵직한 15개 작업 정리.
>
> ROS2 / Docker / ONNX 같은 컴공 일반 용어는 그대로, 특수 알고리즘 명·라이브러리는 풀어씁니다.

---

## 1. ONNX 변환 및 RPi5 Docker 배포 환경 구축

학습된 모델은 PyTorch 런타임 위에서만 동작해 RPi5에 그대로 올릴 수 없었음. 표준 모델 포맷인 ONNX로 변환하고, RPi5에 ROS2 Jazzy와 카메라·모터·LiDAR 드라이버를 묶은 Docker 컨테이너 4개(추론·장애물·합성 제어·모터 제어)를 구성. PC 빌드 이미지가 RPi5에서도 동일하게 작동하게 되어 "PC와 로봇이 같은 환경"을 보장하는 배포 기반이 완성됨.

## 2. 시뮬레이션↔실물 호환성 분기 처리

같은 차선 추종 코드를 Isaac Sim과 실물에서 함께 쓰려는데, Isaac Sim은 cmd_vel을 `Twist`로 받고 실물의 turtlebot3_node(ROS2 Jazzy)는 `TwistStamped`만 수용. 환경변수 `CMD_VEL_STAMPED` 하나로 메시지 타입을 자동 분기시키고, OpenCR 보드의 ROS1 펌웨어를 ROS2용으로 재플래시. 시뮬에서 검증한 코드가 실물에서 별도 수정 없이 그대로 모터를 회전시키는 상태에 도달.

## 3. PC↔RPi5 크로스 머신 토픽 모니터링

RPi5에 모니터가 없어 카메라 영상이나 추론 결과를 실시간 확인하기 어려웠고, ROS2의 멀티캐스트 자동 탐색은 공유기에서 차단되어 PC가 토픽을 발견하지 못함. RPi5 IP와 도메인 포트를 명시한 통신 설정 XML을 PC에 적용해 유니캐스트로 직접 연결하도록 우회. PC의 rqt_image_view에서 `/lane/debug_image`를 실시간 시각화할 수 있게 되어 튜닝 사이클이 크게 짧아짐.

## 4. INT8 양자화 시도 → FP32 ONNX 배포 결정

CPU 추론이 ~2 FPS밖에 나오지 않아, 가중치를 8비트 정수로 압축하는 양자화로 속도를 올리려 시도. 정적 INT8은 mAP@50이 0.000으로 완전히 무너졌고 동적 INT8도 정확도 손실이 커서 차선 추종 자체가 불가. 양자화 경로를 폐기하고 FP32 ONNX 그대로 배포하기로 결정, 속도 문제는 입력 해상도 축소·전용 가속기 칩 도입으로 풀기로 노선 변경.

## 5. Docker Hub 멀티아키텍처 빌드/자동 배포 파이프라인

기존 배포 방식은 PC가 rsync로 코드를 RPi5에 동기화하고 컨테이너에 볼륨 마운트하는 구조라, RPi5가 PC에 종속되고 모델·코드 버전 불일치가 자주 발생. PC에서 buildx로 ARM64 이미지를 크로스 빌드해 Docker Hub에 push하고, RPi5는 `docker compose pull && up` 한 줄로 실행되도록 전환. 코드와 모델이 이미지에 내장되어 RPi5 단독 운영이 가능하고, 시연 환경 이동 시에도 별도 셋업 없이 동일 환경 재현.

## 6. NCNN 추론 엔진 전환 + 320×320 모델 재학습

ONNX Runtime은 x86 CPU 위주로 최적화되어 RPi5에서 효율이 떨어짐. ARM NEON SIMD에 고도로 튜닝된 Tencent NCNN으로 엔진을 교체하고, 동시에 입력 해상도를 640→320으로 줄여 연산량을 1/4로 감소. 같은 합성 데이터로 yolov8n 320×320을 재학습한 결과 mAP@50=0.959 유지, RPi5 실측 FPS는 2 → 13~15로 약 8배 향상되어 임시 실시간 주행 가능 상태에 도달.

## 7. 합성 데이터 다양화 + 2000장 재생성

기존 1000장 합성 데이터는 카메라 위치·조명 변화가 좁아서 학습 진동이 컸고(마지막 20 epoch 표준편차 0.196), 실제 카메라 입력과의 분포 갭도 큼. 데이터 생성 스크립트에서 카메라 위치 ±0.10m, yaw ±15°, 조명 강도/위치/색온도, 가우시안 노이즈/블러를 모두 다양화해 2000장 재생성. 같은 yolov8n 320 모델로 재학습한 결과 mAP@50=0.962 + 학습 진동 6배 감소(표준편차 0.033)로 실주행 안정성이 크게 향상.

## 8. Hailo-8 NPU 하드웨어/드라이버/컨테이너 통합

CPU/NCNN으로는 안정적 30 FPS 확보가 어려워 전용 AI 가속기 칩(Hailo-8)을 도입. RPi5 M.2 슬롯에 보드를 장착하고 PCIe Gen3 활성화 → 커널 모듈 자동 빌드 시스템(DKMS, *커널이 업데이트되어도 드라이버를 알아서 다시 컴파일해 주는 구조*)으로 드라이버 설치 → HailoRT 런타임과 Python 바인딩 설치 → 호스트 측 `/dev/hailo0` 인식 확인 → Dockerfile에 HailoRT 통합 후 컨테이너 내부에서도 NPU 사용 가능. 이 과정에서 발견한 호환성 이슈 7건을 정리해 35분짜리 재현 가이드 문서로 보존.

## 9. NPU 전용 모델 컴파일 (양자화 + 다운사이즈)

NPU는 ONNX를 직접 받지 못하고 칩 전용 실행 포맷(HEF, *Hailo Executable Format*)으로 컴파일된 모델만 실행. PC에 Hailo Dataflow Compiler(Docker)를 설치해 ONNX → 양자화용 캘리브레이션 셋(검증 데이터 100장) → INT8 양자화 → 칩 자원 매핑까지 자동화하는 변환 스크립트 작성. yolov8s 640과 yolov8n 640은 칩의 SRAM 한계로 매핑 실패(`No valid partition`)했지만, yolov8n 320으로 다운사이즈해 컴파일 성공(9.5 MB). 모델 크기/입력 해상도와 NPU 메모리의 관계를 실측으로 학습한 결과.

## 10. NPU 전용 추론 노드 (lane_detect_hailo.py) 구현

HEF의 출력 텐서 구조가 ONNX/NCNN과 달라(검출 헤드 직전에 그래프를 끊은 두 raw 출력) 기존 코드로는 결과 해석이 불가. YOLOv8의 좌표 인코딩 방식인 분포 회귀(*Distribution Focal Loss — bbox 좌표를 16개 bin의 확률 분포로 표현하는 방식*)를 디코딩하고, 표준 앵커 그리드(stride 8/16/32)에 매핑해 픽셀 좌표로 복원하는 후처리 모듈을 작성. 단위 테스트로 정확도 검증 후 기존 ROS2 인터페이스(`/lane/cmd_vel`, `/lane/debug_image`)를 그대로 유지해, 환경변수 `INFER_ENGINE` 하나로 NCNN↔NPU 즉시 토글 가능.

## 11. NPU 실주행 성능 검증 — 30 FPS 안정

NPU 도입 효과를 객관적으로 측정. `hailortcli benchmark`로 NPU 단독 추론 능력 측정 시 **217 FPS / 3.97 ms latency** 확보(NCNN 14.7 FPS 대비 ≈15배). 카메라 입력→ROS2 콜백→cmd_vel 발행까지의 실주행 전체 흐름은 카메라 발행 속도(30 Hz)에 묶여 **30 FPS·콜백 33 ms로 NCNN(15 FPS) 대비 2배 안정**. NPU 사용률은 50% 미만(8 클러스터 중 4개, 활용도 60%)으로 여유가 커서 디버그 발행·추가 후처리 부담 흡수 가능.

## 12. 실세계 파라미터 튜닝 (검출 안정화 + 진동 제어)

시뮬에서 잘 작동하던 파라미터를 실물에 그대로 가져왔더니 INT8 양자화로 인한 confidence 분포 평탄화와 카메라 물리 장착 오차로 차선 외 영역에 박스가 잡히고 좌우 진동이 발생. 검출 신뢰도 임계값(`conf_thresh`)을 0.12 → 0.85로 단계적 상향, ROI를 화면 하단 20%로 축소, 조향 P 게인(`kp_angular`)을 11 → 4로 감소, 그리고 offset에 **지수 이동 평균 필터**(*최근 3~5 frame의 가중 평균으로 부드럽게 만드는 기법*) 적용. 각 변경 영향을 분리 관찰하기 위해 `--lane-only` 모드(behavior/obstacle 노드 제외)도 추가해 디버깅 효율 향상.

## 13. WiFi 대역폭 최적화 — 디버그 이미지 발행 경량화

PUBLISH_DEBUG=1로 시각 확인할 때 800×600 BGR 원본을 매 frame 발행하니 대역폭 1.4 MB/frame × 30 FPS ≈ 42 MB/s 가 발생해 콜백 시간이 33 ms → 74 ms로 늘고 처리 FPS가 30 → 13으로 떨어짐. 디버그 이미지를 320×240으로 축소하고 발행 빈도를 1/3로 낮춰(skip=3) 대역폭을 약 1/18로 감소. PUBLISH_DEBUG=1 상태에서도 처리 FPS 35 유지 + PC에서 rqt 영상 지연도 사실상 사라짐.

## 14. 환경 기동/종료 스크립트 자동화 + 예외 처리

수동 실행 시 매번 4개 컨테이너 + camera_node + 모터 토크 등을 일일이 챙겨야 했고, 커널 자동 업데이트로 NPU 드라이버가 누락되거나 camera_node 좀비가 남는 등 예외 케이스가 자주 발생. `start_nodes.sh`에 5단계 자동 검증(NPU 인식·드라이버 자동 복구 / 컨테이너 4종 / camera_node 좀비 정리 / 모터 토크 자동 활성화 / HEF 로드 확인)과 `--debug` / `--lane-only` / `--no-obstacle` 노드 선택 옵션 추가. `stop_nodes.sh`도 cmd_vel 0,0 선발행 → inference 우선 종료 → camera → 나머지 순서로 안전 종료.

## 15. 안전 정책 + 최종 시연

자동 주행(AUTOSTART) 옵션은 사용자 의도와 무관하게 모터가 움직여 위험할 수 있어 정책적으로 폐기. 주행 시작은 반드시 `docker attach inference-node` 후 `s` 키 입력으로만 가능하게 고정하고, 종료 시 `q` 또는 `Ctrl+P,Q`(detach)만 허용. 직선·곡선·장애물 회피·차선 복귀 시나리오를 통과한 최종 시연 영상을 촬영하고, 14주 진행 과정을 9개 챕터 + 트러블슈팅 11건 + 본 보고서로 정리해 프로젝트를 마무리.
